# 第十轮：跨标签状态与奖励持久化修复

本轮只修复会话、奖励存储和通知批量操作。后端、仿真、依赖及锁文件、课程配置、奖励数值与徽章条件没有变化；没有新增视觉页面或业务。开始时工作区干净，基线为 `5ff13da7a3a26d86f01dd286e4e8041f9008db3f`，继续在当前 main 上开发。

唯一远端为 `shrrrrrrrr/web-frontend-test`。原仓库只读，引用 SHA 仍为 `49c179eed0656b34d8b5a03491c8afd9a9d1de77`（见 SOURCE.md）。

## 修复前证据与确认程度

- 会话：隔离 Edge 两个实际标签，使用临时 SQLite 的真实登录、refresh 和 me 接口。用本测试密钥签发过期 access token 触发客户端刷新，旧实现中 B 的 me 返回 200 后仍掉到登录页，反馈输入消失，断言失败。没有用模拟刷新响应冒充真实后端。后续另覆盖正常主动刷新时钟和真实服务端 401 分支。
- 通知：延迟真实 read-all 请求，期间切换到课程筛选并先读取旧列表，随后放行真实写入。旧实现出现成功横幅，但未读行仍存在，当前筛选没有重新读取，断言失败。
- 奖励：原最小脚本 `node scripts/diagnose-edge-storage-locks.mjs` 在不加载应用/认证的两张空白页运行 25 次，失败编号为 6、8、24（从 0 开始），两页最终均为 80。它证明所观察到的保存结果不可靠，不证明浏览器内部哪个机制存在 bug；这些次数不是总体失败概率。

会话与通知的生命周期原因由代码和上述场景共同确认。奖励采用新持久化契约解决工程问题，没有对 Edge 内部原因作定论。

实现过程中新增的双标签同时刷新测试还暴露了两个问题：一次性 refresh token 被重复使用；随后加入的保护又可能把另一标签短暂的保存中状态误判为失效。分别增加跨标签网络刷新排队、稳定保存事件等待和整枚 token 的账号范围比较后，20 组真实并发刷新通过。等待由保存事件驱动，15 秒上限只负责报错退出，不把超时当成功，也不使用固定 sleep 等待数据碰巧一致。测试中的登录页自动跳转假设、礼品标签名称定位曾导致测试失败，已按实际页面契约修正；没有删业务断言。

## 最终实现

### 同账号轮换保留业务树

`authSession.js` 不再先删除 token / refresh_token / user 再保存。保存中标记防止恢复半套凭据；完整保存后写带 nonce 的稳定事件。任何一步失败仍清理身份键，无法清理时保留阻断标记。

`AuthContext.jsx` 区分首次恢复、真实身份边界和同账号轮换。同账号只后台调用 me 复核，不设置 user=null 或全页 loading，因此反馈、回复、独立反思、筛选和弹窗仍是原来的实例。验证包含 DOM 对象相等及输入文本相等，不靠新增草稿缓存恢复。

退出、切换账号、停用、明确失效和 FORCE_RESET 仍清除旧作用域并提高请求世代。其他标签收到退出时只停止本页，不再反过来清理另一标签刚保存的新登录。旧账号请求及刷新响应迟到均被拒绝。同账号已经成功的业务响应不会因正常轮换被随意丢弃。后台 me 短暂失败保留表单，不能把本地缓存当服务器授权。

`client.js` 保留原主动刷新、401 单次重试、部分保存清理、改密先保存新会话及 session notice 降级。JWT 的 base64url 编码按实际格式读取。Web Lock 仅串行处理跨标签网络刷新；轮到执行时重读并复用已轮换凭据。读取碰到保存中标记时等待稳定保存事件再核验；损坏或未完成保存仍报错。当前 token 范围比较只用于拒绝账号混用，签名、停用、课程和对象权限仍由后端验证。

### 奖励由原生事务保存

- 数据库：`star-voyage-rewards`，版本 1，对象仓库 `accounts`，主键为字符串 accountId。每条记录包含 schemaVersion、initialized、source、initializedAt、revision 和原奖励快照。
- `rewardModel.js` 只负责原有规则；`rewardDatabase.js` 管连接和事务；`rewardAdapter.js` 继续提供 `load/redeem/reset`。没有新增库、正式积分后端或新的奖励规则。
- 兑换在一个 readwrite 事务中读取最新快照、检查同次请求编号、验证余额/库存/限次、扣分和写明细。只在事务 complete 后返回成功；put success 后事务中止仍失败，原已提交数据不变。
- 重置在同一仓库事务内写初始快照并保留初始化记录，不删除账号记录。无需先 load 成功；经界面确认后可恢复损坏的 v1 来源、损坏的快照或初始化元数据，只处理当前账号。
- 取消尚未完成的事务会 abort；提交后取消不能撤销已保存事实。页面及账号卸载后的旧回调不再显示结果。没有 localStorage 或内存余额回退。
- 原契约保持：初始 120；笔记本 40 / 库存 3 / 限兑 2，模型 160 / 库存 2 / 限兑 1，贴纸 20 / 库存 0 / 限兑 1；两枚徽章固定预置。与练习、作品、试飞和正式积分均不联动。

依据：[IndexedDB 事务调度](https://w3c.github.io/IndexedDB/#transaction-scheduling)、[complete 事件](https://w3c.github.io/IndexedDB/#dom-idbtransaction-oncomplete)、[Web Storage 交互边界](https://html.spec.whatwg.org/multipage/webstorage.html#introduction)。数据库事务是持久化裁决点，广播和 React 状态不是。

### 旧记录与同步边界

旧 `star-voyage:rewards:demo:v1:${accountId}` 只在数据库没有当前账号记录时读取。合法余额、请求编号、明细、时间及其他合法原字段保持原值，迁移不重新发分。迁移准备在事务外完成，写入事务内再次检查是否已有账号，避免两个首次打开标签覆盖已提交兑换。

原 v1 保留为备份；新数据库是唯一有效来源，不双写、不每次导入、不批量读写别的账号。已有数据库记录时不再访问旧存储，即使旧存储读取被禁也能加载。迁移失败不提前写 initialized，损坏来源不会被静默重置。明确重置后再加载、刷新或新开标签也不会重新导入旧记录。

旧版本已打开标签必须刷新。旧代码对 v1 的写入不会与新数据库合并；新页检测到这类 storage 事件会说明边界。回退旧前端代码可能重新看到旧备份而不是新兑换，因此不能把代码回退当数据回滚；保留数据库与备份，升级相关页面后核验。当前没有对两个版本的余额做双向同步。

顶栏和页面仍共用账号 store。BroadcastChannel 只发送 accountId 变化信号，接收后重读数据库；即使消息附带伪造余额也不采纳。同页通知、焦点返回、迟到读取保护保留，最后订阅卸载时关闭通道并移除监听。数据库失败、保存成功后读取失败、广播不可用分别提示；广播失败不改写已提交结果，其他页可以返回页面后重读。

### 通知批量操作跟随当前列表

批量 pending、成功/失败提示和确认框提升到账号级父组件。筛选及分页可继续切换；写入确认后调用当前挂载列表的 reload，再刷新全账号未读数。回读期间又切换筛选时跟随当前读取者，最多三次后给出“显示暂未刷新”和重读入口，不无限循环。

写失败提示不会随旧 Results 卸载丢失；写成功但回读失败说明已完成，只重发 GET。全账号批量范围、清理确认、最后页回退和未读数语义不变。清理确认框在写入时保留，阻止背景操作；退出或换账号后旧批量回调不能影响新账号。

## 启动、证据与边界

日常仍在 app 目录运行 `npm run server` 和 `npm run dev`；沿用 README 的本地初始化步骤。本轮没有需要执行的后端迁移脚本。已有奖励数据在首次访问当前版本时自动按账号迁移；不要为验收重置真实开发数据库。
